# 需求澄清（requirements 阶段）

在进入静态 H5 预览（plan）之前，先澄清开发者的**真实业务需求**，产出 `activity/requirements.md` 并获得开发者确认。全程先谈业务事实，后端实现细节确认后再落。

## 操作速查（先跑通机制，再读正文）

- 当前阶段：`python3 skills/runbook/state.py current`（未初始化会提示，先 `state.py init`；阶段指引会自动注入，无需手动跑）
- 决策树：`state.py tree` 看前沿 → `state.py decide <id> <选项>` 记录（依赖未定会被拒绝）
- **decisions.json 首版由 Agent 按草案创建**（destination + 决策节点，预填项标「(默认)」）；创建后只经 `state.py decide` 修改，不要手改
- 确认：`state.py confirm requirements` → `state.py advance`
- 机制不会用：看本文件；**禁止读 `skills/runbook/` 源码**

## 目标

- 锁定：活动目标、用户能做什么、规则细节、数据需求、素材清单
- 产出：`activity/requirements.md`（需求单，含**部署决策**与**静默假设清单**）+ `activity/decisions.json`（决策树，由 `state.py decide` 维护）
- 门禁：决策树待定清空 + 需求单含静默假设 + 开发者确认后 `state.py confirm requirements` → `advance`。部署决策按技能包能力触发且**时序靠后**（见「部署确认」）：技能包含云服务能力 → 创建 `status=deferred` 的部署节点（不进入前沿），需求轮只问雏形，存储方式确认留到 plan 静态预览获得开发者确认后（引导式）；技能包不含云服务技能 → 创建决策树时直接预填已决（choice=B + note 依据），不进入前沿、不提问，**但需求单「部署决策」节必须写入「本地存储告知」并主动告知用户（门禁强制）**

## 引导流程（先给可改的答案，再问真问题）

开发者是「看方案给反馈」的人，不是「从零回答问题」的人。不要上来就提问；**先写一版完整的草案，让开发者对着草案说"要改哪里"**。草案本身就是最强的问题——开发者看到「你预填的是投票但我要的是抽奖」，一句"不是这个"就把真实意图暴露出来了。

1. **元问题优先**：先问一个元问题——「有参考活动或类似案例吗？」（有就提供链接/描述，或直接说"按去年那个来"）。有参考 → 基于参考预填草案，差异点显式列出；没有 → 基于下面的活动模式默认库预填。
2. **静默探索**：读 `activity.json`（身份）、`credentials.json`（部署凭据现状）、已有路由/代码、技能市场（`skills/colorbox-skill/SKILL.md` 能力总览，**只读总览，禁止批量浏览子技能 SKILL.md**，选型在 plan/implement 做）；**检查技能包是否含云服务技能**（`skills/act-cloudbase/` 目录存在与否，决定部署决策问不问，见「部署确认」）；部署目标用 `node skills/act-cloudbase/scripts/query-cloudbase.js`（只读）确认该 activityId 是否已有环境（仅技能包含云服务能力时）。AI 能查到的决不发问。
3. **写完整草案**：先判定活动类型（从一句话意图识别，见「预填分级」的类型清单），再直接生成 `activity/requirements.md`，按预填分级填好默认值，同时用 `state.py decide` 初始化 `activity/decisions.json` 决策树（预填项标「(默认)」）。
4. **轻量呈现**（一轮，一次发完，开发者视角）：
   - 一句话摘要（活动最终长什么样，默认值藏在里面——开发者不同意会直接说）
   - 编号题 ≤3（每题一句，问开发者知道且在乎的；不带「回 N 个数」「无异议」等元指令）
   - 默认项**不在提问轮出现**，放到最终确认那一句
   示例见「提问格式」。
5. **多轮收敛，业务在前、页面在后、部署靠后确认**：第 1 轮只问业务意图（该类型的拍板点，见「预填分级」）；第 2 轮（业务确定后）做**雏形引导**——先给功能清单并只问「要不要先看个雏形模板」（**不夹带部署/存储问题**），开发者要看 → 直接收敛进 plan 产出静态预览，不再重复示意或追问（见「功能确认」）；部署决策按技能包能力触发且时序靠后：技能包含云服务能力 → 存储方式确认放到 plan 静态预览确认后、进入技术方案设计前（引导式，见「部署确认」与 plan-confirm.md）；技能包不含 → 预填本地存储并**主动告知**（需求单「部署决策」节写「本地存储告知」，门禁强制），不提问。
6. **收敛确认**：开发者答完 → `state.py decide` 逐项记录 → 重算前沿 → 收敛后 `state.py confirm requirements`。

**结束标准**：`state.py tree` 前沿为空，且需求单含静默假设清单且开发者**明确确认**（不是"没人反对"）。不是「问题问完了」，而是「没有东西被静默假设」。

## 预填分级（先写默认，再留真问题）

预填是效率来源，也是带偏风险。必须分级：

| 层级 | 内容 | 处理 |
|------|------|------|
| **必须问，禁止预填** | 仅触碰合规红线时：涉及钱（支付/奖励/抽奖）、隐私（采集手机号/身份证等敏感信息）、未成年（面向未成年人） | 触碰才进拍板清单，每题带推荐 |
| **可预填默认**（标「默认」） | 次数限制、是否登录、可否修改、排序方式、风控强度、失败提示语等**可逆业务细节** | 写进需求单并标「默认」，开发者一句话可改 |
| **不确定就待澄清** | 不在已知活动模式里、猜不准的点 | 写进「待澄清」，不硬猜、不拆成假问题 |

常见活动模式默认库（预填依据 + 拍板点清单；不在库里的类型进「待澄清」，不硬套）：

| 类型 | 默认规则（可预填） | 该问什么（拍板点） |
|------|-------------------|--------------------|
| 投票 | 每人 1 次｜需登录｜提交后不可改｜按票数实时排行 | 时长？名单谁定？奖品？ |
| 抽奖 | 每人每日 1 次｜需登录｜开奖时间固定｜中奖名单结束后公布 | 开奖时间？奖品池（几档/多少份）？参与门槛？ |
| 报名 | 每人 1 次｜需登录｜提交后可改（活动开始前）｜名额先到先得 | 报名窗口？名额上限？要提交什么信息？ |
| 打卡/签到 | 每日 1 次｜需登录｜可补卡 N 次｜按连续天数排行 | 活动周期？补卡次数？排行维度？ |
| 排行榜 | 分数即成绩｜需登录｜取最高分｜实时排行 | 计分规则？能否重复参与？榜单展示范围？ |

Agent 流程：**一句话意图 → 判定活动类型 → 取该类型「默认规则」预填 + 「该问什么」出题 → 套通用骨架**；类型识别不了就进「待澄清」，不硬套其他类型的问题。

敏感项（钱、合规）**永不默认**，永远进拍板清单；部署决策按技能包能力触发且时序靠后（见「部署确认」）：技能包含云服务能力 → 需求轮不提问，部署节点标 deferred，静态预览确认后再确认；技能包不含云服务技能 → 预填已决（choice=B + note 依据），不进拍板清单。

## 轮次制提问（一轮问完整前沿，不是一次一问）

决策之间有依赖：B 的选项会随 A 的选择变化，就先问 A。决策树**不是写在提示词里的纪律，是脚本机制**：

- 每个决策是 `activity/decisions.json` 里的一个节点：`id / question / options / recommend / depends_on / status / choice`
- `python3 state.py tree` 计算并显示**前沿**（依赖已定且可问的待定项）
- **提问前必须先 `python3 state.py present --frontier`**（或 `present <id...>`），把本轮要问的决策标记为「已展示」；未展示的决策 `decide` 会被脚本拒绝——**这是防止代答未确认项的硬闸**（如开发者只回了「确认」，未展示的部署决策也不许落定；部署确认前必须先 present）
- **present 后必须等开发者明确回复再 `decide`**：present 只是「已展示」标记，不是开发者确认；展示与落定之间没有开发者回复（哪怕回复是「可以/不行/按推荐」）就 `decide`，属于替开发者拍板，门禁会以「部署决策未经开发者确认」拦截
- **问题编号必须一一对应决策 id**（开发者消息用 1/2/3，内部记录用 D1/D2…），禁止自创 Q0/Q1 等编号；"参考活动"这类草案字段写在确认单正文里，不编号进提问轮
- **一轮问完整前沿**：全部编号后一次发问，每题带推荐；开发者按编号一次答完（"1 A，2 B，3 按推荐"），**不要逐题等待**
- 开发者回答后 `python3 state.py decide <id> <选项>` 记录；**依赖未定、未展示、`if_choice` 不满足的决策都会被脚本拒绝**，不会出现在前沿
- 答案会重排依赖：下一轮重算前沿，只问新解锁的问题

拍板点控制：**每轮 ≤3 个**（开发者视角，超过就是过载）；超过说明预填不够激进，先把可默认的吸收进草案。复杂活动（奖品池多档、结构复杂）可超，但必须仍在一轮内发完。目标 2~3 轮收敛。

## 防点头确认（确认必须带信息量）

开发者时间紧，会倾向直接回「确认」——如果确认是点头，等于什么都没锁定，交付完才发现「这不是我要的」。所以确认动作必须设计成：**同意要显式，不同意要零成本**。

- **默认项放确认句，不放提问轮**：默认项混进问题清单会让开发者过载，还会把关键假设埋在噪音里。只在最终确认时给一句短的：「需登录、投完不可改、不实名——有问题说一声，没有就确认」。只列有风险的项。确认句内容取自需求单「静默假设」小节，保持两者一致。
- **沉默不算同意**：不回复、不逐项放行的默认项**不算已确认**；门禁只认 `state.py confirm` 的明确动作。
- **确认要留证据**：收到开发者明确回复后，先把原话写入 `activity/confirmations/<阶段>.md`（如 `activity/confirmations/requirements.md`），再执行 `state.py confirm <阶段>`；缺证据时 confirm 会被状态机拒绝。每个开发者确认阶段（requirements/plan/security-review/deploy/deliver）都必须这么做，禁止用「自检通过」代替开发者确认。
- **邀请指出不同意**：确认姿势是「哪里和你想要的不一样，直接说，一句话就改」，不是「没问题就回复确认」。开发者指出异议才是本轮真正有价值的信息；没有异议的会话要警惕，不要当作完美收敛。
- **感觉型问题不硬聊（ungrillable → 预览）**：凡是「这个页面感觉对不对」「好不好玩」这类靠聊天答不了的问题，不要反复追问，标记为「留到 plan 阶段静态预览确认」，直接推进。开发者需要看到东西才能回答，这正是 plan 阶段先出 H5 预览的原因。
- 开发者答「不知道/随便」时，**按推荐选项记录并标记「按推荐默认」**，该点进入确认句让开发者看到，确认后即视为已决——不替他偷偷拍板，也不让流程卡死；只有确实无法给推荐的点才标「待开发者定」。能靠预览解决的挂到预览阶段。

## 功能确认（业务确定后的第二轮：从零设计视角，先给雏形）

假设开发者**从来没实现过这类功能**、是从头设计——第二轮的目标不是讨论技术或部署，而是先让开发者"看到"东西。给一份**功能清单**（页面大概长什么样、用户能做什么/看到什么，纯业务语言，无技术词），并问一句「要不要先看个雏形模板 / 一版初步页面效果？」。

- **机器强制（新建必问）**：新建场景（工作区根目录无 `h5/index.html`）决策树必须含 `kind=prototype` 节点（「要不要先看个雏形模板」，A=要看/B=不用），`present` 后等开发者回复再 `decide`，未落定 requirements/plan 门禁不放行；**已有 HTML 的改造场景不生成该节点、不问**（见 plan-confirm.md「两条分支」）。雏形节点自动排在其它业务决策之后进入前沿（业务在前、雏形在后）
- **内容**：功能清单 + 雏形预览引导（布局/功能点示意即可）
- **预览边界**：完整静态 H5 预览在 plan 阶段产出（门禁要求 `h5/index.html`）；本阶段不提前产出完整 HTML
- **只问雏形，不夹带部署问题**：本轮只问「要不要先看个雏形模板」，**禁止同时问数据存储/后台**（如「要保存数据吗」）——那是两个独立问题，混在一轮里会让开发者对没见过的页面做技术判断；存储确认放到 plan 预览确认后（见「部署确认」）
- **收敛**：开发者确认功能（或表示要看雏形）即视为功能已定 → 直接收敛进入 plan，**不再在本阶段重复描述页面、不再追问**；plan 阶段直接产出可点击的静态预览让开发者看效果
- **低风险短路**：内部调试、固定参数、纯展示、不记录不限制这类零成本场景，功能清单本身就是方案，开发者说「可以/看看效果」即完成确认，走告知式（见「确认强度分级」）

## 部署确认（技能包含云服务能力才问；不含则默认本地存储并主动告知）

部署决策只做一件事：**防止把需要云端保存的场景按本地/纯展示交付，或反过来**。**触发条件 = 用户技能包是否包含云服务技能**（`skills/act-cloudbase/` 目录存在）：

- **技能包含云服务能力 → 必须问、必须等开发者确认，且时序靠后**：无论业务事实看起来多「显然纯静态」（如个人专属卡、不记录、不限次），都禁止用「推导依据」预填落定——云端保存涉及资源与成本，属于必须开发者知情确认的不可逆动作。**需求阶段不提问**（部署节点标 `deferred`），确认放在开发者看完雏形之后：
  - **时机**：plan 阶段静态预览获得开发者确认之后、进入技术方案设计（implement）之前。完整时序：① 需求轮只问「要不要先看个雏形模板」→ ② plan 生成静态 `h5/index.html` → ③ 开发者看预览并确认「没问题可以继续」→ ④ 此时单独确认存储方式（引导式，见下）→ ⑤ 才进入技术方案设计/实现
  - **性质**：**引导式选择，不是抽象二选一**。「存下来」有很多种存法（本地 vs 云端），用户不知道怎么选——**禁止甩「要不要存」这种用户无法判断的问题**；要讲清两种存法的区别，并**按实际情况给出推荐**：
    - **云端保存**：数据存在服务器，跨设备、可做真实排行/防重复（需要云服务能力）
    - **本地保存**：数据只存在用户自己设备/浏览器，换设备或清缓存会丢、无法跨用户共享
    - **推荐依据**：业务需要跨用户共享/持久/限次/排行 → 推荐云端；纯个人自嗨、数据可丢 → 推荐本地
  - **示例句式**（先讲业务，再给存法 + 推荐，最后确认）：

```text
要记下每位球迷的打分、算平均分、每人只能打一次——这些数据需要真正保存下来。
保存有两种方式：
1 云端保存：数据存在服务器，跨设备、实时排行、可防重复（你有云服务能力，我可以直接接入）
2 本地保存：只存在用户自己的设备上，换设备或清缓存会丢，也看不到真实的整体数据
你的场景需要「每人限一次 + 实时平均分/排行」，我建议用云端保存。按这个来可以吗？
```

开发者明确回复后由脚本记录（提问前**必须已 present**，present 后必须等开发者回复再 decide）：

```bash
python3 state.py present D4       # plan 预览确认后、进 implement 前执行；提问前必须已 present
python3 state.py decide D4 A      # A=云端保存 / B=本地保存
```

- **开发者主动提前答复时**：需求轮不主动问，但若开发者在看预览前自己提出「要保存数据/要后台」，可当场 `present` + `decide` 落定（A=云端保存 / B=本地保存），无需拖到 plan；门禁同时接受 `deferred` 与「resolved + presented」两种状态，落定后 plan 不会重复问。
- **技能包不含云服务技能 → 不提问，但必须主动告知（告知式，不是问题）**：用户没有云服务能力，云服务不是可用选项 → 创建决策树时把部署节点预填为已决（`choice=B` + `note=技能包不含云服务部署能力，默认本地存储`），不进入前沿、不提问；**同时必须主动告诉用户**（业务语言，禁止静默）并写入需求单「部署决策」节的「本地存储告知」行（门禁强制检查），示例话术：

```text
当前没有云服务能力：数据只能存在本地（浏览器/本机），换设备或清理缓存会丢，也无法做真实的跨用户排行。
我先按「本地保存/纯展示」做，后续需要云端保存再加。
```

- **判断标准**：技能包含云服务能力 → 必问（引导式）；不含 → 必不问、必告知。不按「业务看起来像什么」自行跳过或补问。

## 确认强度分级（确认跟着风险走，不是每轮必答）

确认是给「不可逆、有成本、有风险」动作上的保险，不是流程仪式。按场景分级：

| 场景 | 确认方式 |
|------|---------|
| 低风险（内部调试/纯展示/固定参数/随时可改） | 告知式：方案一句话 + 直接做，做完给效果，开发者看了再说改哪里 |
| 中风险（涉及已有数据、规则调整） | 预览 + 一句确认（原/新对照） |
| 高风险（花钱/动真实数据/对外发布/不可逆） | 前置完整确认，必须开发者明确回复 |

判断标准：做错了能直接改回来、不花钱不泄露数据 → 默认直接做，不做前置确认。

> **部署决策例外**：确认强度分级只适用于业务改动本身；「要不要后台/云服务」是独立门禁，无论业务多低风险，只要技能包含云服务能力就必须走「部署确认」提问（见上）。

## 提问格式（轮次制，一次一轮，开发者视角）

开发者的回复成本决定收敛速度。话术标准：**问题短到像同事在问——不解释流程、不教怎么回复、不编造细节**。**示例只校准语气，不承载内容**：问题从「预填分级」的类型清单取，不照抄示例台词。

通用骨架（任何活动类型都套这个）：

```text
我按「<活动名>」起个稿：<一句话：时长 + 核心规则 + 展示/奖品>。
几件事你定一下：
1 <该类型第一个拍板点>？
2 <该类型第二个拍板点>？
3 <该类型第三个拍板点>？
```

演示示例（仅话术示范，问题内容必须按活动类型替换，禁止照抄）：

```text
我按「本周最佳球员投票」起个稿：7 天、每人每天给 1 名球员投 1 票、实时排行、第一名送球衣。
三个事你定一下：
1 时间：3 天还是 7 天？
2 名单：你给，还是开放提名？
3 奖品：有的话是什么？（先说占位）
```

规则：
- **最终消息以话术直接开头**：第一句就是「我按…起个稿」，禁止任何自报进度前缀——不加「草案已就位」「决策树已初始化」「已标记展示」「下面是给开发者的确认单」这类元叙述；文件路径、机制命令（state.py/decide/present）、决策树/前沿、present 标记等内部状态只存在于工具输出与 `activity/` 产物，**永不进开发者可见消息**
- **对开发者的编号用 1/2/3**：内部决策 id（D1/D2…）只用于记录与回答映射，开发者消息里不显示 D 前缀（写「1 时间：…」而非「D1 时间：…」）
- **先判定活动类型**：从一句话意图识别（投票/抽奖/报名/打卡/排行榜…），取该类型的默认规则与拍板点清单套进通用骨架；识别不了进「待澄清」，不硬套
- 第 1 轮只问业务（该类型的拍板点）；第 2 轮是雏形/功能引导；部署确认放功能确认之后（仅技能包含云服务能力时，见「部署确认」）
- 每题一句，问开发者**知道且在乎**的；删掉元指令（「回 N 个数」「无异议」这类话），问题格式天然可答
- 推荐只在开发者能判断的地方给（时长、要不要后台等）；**禁止编造细节**（如具体奖品、具体名单）
- 默认项不在提问轮出现，放最终确认那一句（见「防点头确认」）
- 分支影响后续问题时，一句人话预告即可（如「名单开放提名的话，我后面会再问提名门槛」）

## 决策树怎么维护（机制，非提示词）

`activity/decisions.json` 结构：

```json
{
  "destination": "一句话目的地",
  "decisions": [
    {
      "id": "D3",
      "question": "每人可以提交几次？",
      "options": {"A": "1 次", "B": "每日 1 次", "C": "不限"},
      "recommend": "A",
      "depends_on": [],
      "status": "open"
    },
    {
      "id": "D1",
      "kind": "deployment",
      "question": "要记录票数并限次，需要专属云服务吗？",
      "options": {"A": "需要（推荐）", "B": "不需要"},
      "recommend": "A",
      "depends_on": ["D3"],
      "status": "deferred",
      "note": "需求轮不提问，plan 静态预览确认后再确认"
    },
    {
      "id": "D4",
      "question": "提交后允许修改吗？",
      "options": {"A": "不可修改", "B": "可修改"},
      "recommend": "A",
      "depends_on": ["D3"],
      "if_choice": {"D3": "A"},
      "status": "open"
    }
  ]
}
```

- 分支：`if_choice` 表示「仅当某前置决策选了某选项才问」；不满足的节点永不进入前沿（例如 D3 选「不限」就无需问 D4）
- 部署节点**按技能包能力生成且时序靠后**：技能包不含云服务技能（无 `skills/act-cloudbase/`）→ 首版决策树直接预填 `choice=B` + `note=技能包不含云服务部署能力，默认本地存储`，不进入前沿，**并必须在需求单「部署决策」节写入「本地存储告知」主动告知用户**；技能包含云服务能力 → 必须生成 `kind=deployment` 节点并标 **`status=deferred`**（不进入前沿、不计入未决），plan 静态预览获得开发者确认后、进 implement 前，引导式确认存储方式（云端保存/本地保存，讲清区别 + 按业务推荐）后由 Agent 记录（`present` + 等回复 + `decide`），**禁止在需求轮提问、禁止预填落定**；部署节点**禁止配置 `if_choice`**（只要技能包含云服务能力就必问，不随业务选项剪枝；`depends_on` 仅用于控制前置业务决策先落定），误配导致节点被 `skipped` 会被门禁 fail-loud 拦截
- 雏形引导节点（仅新建场景生成）：`{"id": "DP", "kind": "prototype", "question": "要先看个雏形模板吗？", "options": {"A": "要看（推荐）", "B": "不用，直接做"}, "recommend": "A", "status": "open"}`——自动排在其它业务决策之后进入前沿（业务在前、雏形在后），`decide` 落定后 requirements/plan 门禁才放行；已有 HTML 的改造场景不生成该节点
- 代答纪律：**禁止无依据代答**——有需求单/开发者原话支撑的推导记录允许（必须写 `note` 依据）；没有任何事实依据时禁止替开发者拍板
- **部署目标不是决策节点**：环境链接/EnvId 靠静默发现（`credentials.json` + `query-cloudbase.js` 只读查询）确认并写进需求单「部署决策」节，决策树不生成「环境用哪个」这类提问节点
- 每轮：先 `state.py tree` 看前沿 → **一轮问完整前沿（编号 + 推荐）** → `state.py decide` 逐项记录 → 再 `tree` 重算，直到前沿为空
- 文件只经 `state.py decide` 修改，不要手改；手改会造成门禁与树不一致

## 需求单模板（activity/requirements.md）

```markdown
# 【活动名】需求澄清单

## 一、业务目标
（一句话说明目标与主题）

## 参考活动
（开发者提供的参考案例/链接；没有就写「无，按默认草案」）

## 二、用户能做什么
- （打开页面看到什么）
- （能点什么、完成后看到什么）

## 三、活动规则
- （默认项按活动类型替换，见「预填分级」；下面只是示例）
- 每人：1 次（默认） / 每日 1 次 / 不限
- 提交后：不可改（默认） / 可改（窗口）
- 时间：起止时间 / 无限制
- 登录：必须登录（默认） / 可匿名
- （依赖存储/登录的项，确认前标「待定：取决于存储方式」，禁止写死成既定规则）

## 四、数据与展示
- 记录：投票记录、报名信息、用户参与记录…
- 展示：实时票数排行 / 结束后公布

## 五、素材清单
- （名单 / 图片 / 文案 / 截止时间；未提供则「先用占位」）


## 部署决策
- 云服务：需要（云端保存）/ 不需要（本地保存，无云服务能力时默认）
- 存储方式：云端（真实记录、跨设备、可排行/防刷）/ 本地（仅本机/浏览器，换设备或清缓存会丢、无法真实跨用户排行）
- 一句话理由：（如：需要记录每人 1 次投票、实时排行；或：技能包不含云服务部署能力，默认本地保存）
- 本地存储告知：（无云服务能力时必填，门禁强制检查）已主动告知用户——没有云服务能力，数据只能存在本地，换设备/清缓存会丢，无法真实跨用户排行

## 不做范围
- （明确排除的玩法/能力，如：不做积分、不做多活动互通）

## 待澄清
- （还没想清/开发者答不上来的点，能靠预览解决的挂到 plan）

## 静默假设（未问即默认，一句话可推翻）
- （如：默认移动端优先；默认不要求实名/风控）
```

## 与后续阶段的关系

- 云服务=**需要**：plan → implement（SQL+函数+接 `ColorboxAI.cloud.request`）→ security-review（发布安全审查）→ deploy（建表/函数/网关）→ test（接口冒烟）→ deliver
- 云服务=**不需要**：plan → implement（纯静态 H5 完成，可接虎扑现有业务能力 `ColorboxAI.request`）→ security-review（发布安全审查）→ deploy（声明无需部署）→ test（页面/静态自检）→ deliver

> 云服务=**不需要** 时交付纯静态 H5，**严禁假后端**：不写假接口、不用 localStorage 冒充、不部署空壳函数。

## 用词指导（非技术化）

对开发者说业务语言，禁止出现：表名、字段名、路由、云函数、网关、PostgreSQL、puid、Bearer、迁移、部署目录、`activity/` 路径、技能名/API 名等。例如：

| 对开发者说 | 不要写 |
|----------|--------|
| 打开页面就能看到候选人列表和票数 | `GET /candidates` |
| 登录后可以投票 | `POST /vote`、`ensureAuth` |
| 每个用户只能投 1 票 | `unique(puid)` |
| 投完后按钮变灰 | 前端状态管理 |

**同时禁止问「用哪个能力实现」**：能力选择是 Agent 在技能市场里的事，不是开发者该答的。

### 开发者可见消息分级（只发两种消息）

对开发者只发两类消息，**其余执行细节一律不进聊天**（写进 `activity/` 产物即可）：

1. **决策请求**：必须业务语言、带推荐、≤3 题（业务拍板点如时长/名单/奖品；部署确认在功能确认后单独发，见「部署确认」，示例「要不要后台帮你记录每次投票，防止一个人投很多次？」）。
2. **结果告知**：一句话业务结果（如「页面做好了，点这个链接预览」）。

**动作黑名单（对开发者永不出现）**：分支、门禁、advance/confirm/decide、自检/预扫描、决策树/前沿、EnvId、credentials.json、物理路径、候选环境数、MCP、云函数、PostgreSQL、路由、manifest 等机制词。确认单里只放**可点击的预览链接**，不写「绝对物理路径 /Users/...」这类文字。

## 改动幅度（对已有活动做调整时）

| 幅度 | 含义 | 要确认吗 |
|------|------|----------|
| 小改 | 玩法不变，只修界面或展示 | 告知即可 |
| 加信息 | 多记一项内容，旧数据保留 | 展示预览并请确认一句 |
| 改规则 | 改参与/提交规则，或改删已有信息项 | **必须确认** |
| 重做 | 和线上活动对不上，或等于推倒重来 | **必须确认，默认先停** |

「改规则」「重做」：未确认前禁止生成 SQL/云函数，禁止部署云服务。
