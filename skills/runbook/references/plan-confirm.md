# 业务计划与开发者确认

在创建开通真正云后端前，先生成**数据写死的纯静态 H5 页面**（`h5/index.html`），并给开发者发一份包含页面预览说明的**业务确认单**。确认单以业务事实为准（界面体验、玩法、规则、数据和素材），后端实现细节确认后再落。

## 两条线，不要混

| 给谁看 | 写什么 | 什么时候写 |
|--------|--------|------------|
| **开发者** | 纯静态 H5 预览、用户能做什么、规则、对已有数据的影响、需要开发者提供的素材 | 第 3 步，默认生成静态 H5 后发确认单 |
| **Agent 内部** | 建表 SQL、云函数、路由映射、真实部署步骤 | 第 4/5 步，收到开发者「确认」后再生成与部署，**不发给开发者** |

第 3 步默认先生成纯静态 H5 页面供本地双击预览，只锁定**UI体验与业务事实**（视觉、玩法、次数、时限、是否影响旧数据）。表名、API 路径由 Agent 在第 4 步根据业务事实自行决定，无需写进确认单。

## 两条分支（新建 vs 已有改造）

进入第 3 步先判定：

- **新建**：`h5/index.html` 不存在（或开发者给了全新需求）→ 生成完整静态预览，走下方「开发者确认单模板」。**前提**：requirements 阶段已问过雏形引导并落定（`kind=prototype` 节点已 `decide`，门禁强制，未问无法进 plan）——开发者已同意「先看雏形」才会走到这里。
- **已有改造**：index.html 已存在，或开发者给了参考/线上活动（改动幅度见下）→ **以现有 index.html 为基线改动**，产出改动版 + `activity/plan/changes.md` 改动点清单（每条：位置 / 原样 / 新样），确认单用「三问结构」。**不需要雏形引导提问**（不生成 prototype 节点）。

已有改造**禁止从零重写**；「重做」类（等于推倒重来）必须先停，给开发者改动对照并确认后才动。

## 怎么做

0. **判定分支**：按上面的规则确认是新建还是已有改造。
1. **新建**：在 `h5/index.html` 生成数据写死的静态页面（无网络与 SDK 依赖）。
   **已有改造**：读现有 index.html 为基线，按需求改动产出改动版 + `activity/plan/changes.md` 改动点清单。
2. **展示完整路径（不调起界面调试工具）**：
   - Agent 生成/改动 HTML 后，**禁止自动调起浏览器或任何界面调试工具**（`open`/`start`、Chrome MCP、DevTools、Playwright、截图等）自测页面正确性——页面正确性靠静态结构自检 + 开发者确认；
   - 确认单中**输出可点击的 Markdown file 链接**即可（例如：`[index.html](file:///绝对路径/h5/index.html)`），由开发者自行打开预览；**不要**再写「绝对物理路径 /Users/...」这类纯文字路径（开发者用不到）。
3. **看线上已有什么、本次打算做什么**（已有改造时对照基线，逐条列出改动点）。
4. **判断改动幅度**（见下表，**分类仅供 Agent 内部判断，不要写给开发者**）。
5. **按「确认强度分级」输出**：小改→两行告知；加信息/改规则→预览 + 确认句或原/新对照；重做→先停 + 完整确认单。
6. **存储方式确认（技能包含云服务能力时，先于技术方案设计；引导式，不是抽象二选一）**：预览获得开发者确认后、进入第 7 步建后端之前，**单独**向开发者确认存储方式——「存下来」有很多种存法，用户无法直接判断，**必须讲清两种存法并给出推荐**：**云端保存**（数据存在服务器，跨设备、可做真实排行/限次；需要这些 → 推荐云端）vs **本地保存**（只存在用户自己设备/浏览器，换设备或清缓存会丢、无法跨用户共享；纯个人自嗨、数据可丢 → 推荐本地）。**禁止甩「要不要存」这类抽象问题**；先 `state.py present` 部署节点，等开发者明确回复再 `state.py decide`（A=云端保存 / B=本地保存）。**禁止与雏形问题一起问、禁止在需求轮问**；确认结果同步进需求单「部署决策」节。
7. **「改规则」「重做」类**：等到回复「确认」再建后端 SQL/云函数、再部署真实云服务。
8. **重新确认**：开发者提任何修改后，改完必须**重新走 `state.py confirm plan`**，前次确认作废；不要边做边改规则。
9. **确认留证据**：收到开发者「确认」后，先写 `activity/confirmations/plan.md`（开发者原话），再 `state.py confirm plan`；缺证据 confirm 会被拒绝。
10. **对开发者只说业务结果**：确认单之外不做执行播报；「新建分支」「推进到 X 阶段」「门禁通过」等动作话术**禁止发给开发者**，最多一句「方案已确认，我继续做」。

## 改动幅度（Agent 内部）

| 幅度 | 含义 | 要确认吗 |
|------|------|----------|
| 小改 | 玩法不变，只修界面或展示 | 告知静态 HTML 效果即可 |
| 加信息 | 多记一项内容，旧数据保留 | 展示预览并请确认一句 |
| 改规则 | 改参与/提交规则，或改删已有信息项 | **必须看预览并确认** |
| 重做 | 和线上活动对不上，或等于推倒重来 | **必须看预览并确认，默认先停** |

「改规则」「重做」：未确认前禁止生成 SQL/云函数，禁止部署云服务。

## 确认强度分级（按改动幅度）

| 幅度 | 确认方式 |
|------|---------|
| 小改 | 预览 + 两行「改了什么/没改什么」，回「可以」即可，不用完整确认单 |
| 加信息 | 预览 + 确认句（规则要点一句） |
| 改规则 | 预览 + **原规则/新规则对照** + 确认 |
| 重做 | 默认先停，给改动对照 + 完整确认单，明确「等于推倒重来」 |

## 已有改造：三问确认结构

给已有活动做改动时，开发者关心的不是新版长什么样，而是「你动了我什么东西」。确认单按三问组织：

1. **改了什么**（逐条：位置 / 原样 / 新样，UI 改动描述 before/after）
2. **没改什么**（明确不动的规则与数据，让开发者放心）
3. **数据和规则受不受影响**（旧数据保留 / 受影响 / 历史记录是否清零）

## 开发者确认单模板

标题用活动名，例如 `【人气投票】活动方案与预览页面，请确认`。

```text
零、页面静态预览
- 已生成静态 H5 预览文件：[index.html](file://<绝对路径>/h5/index.html)
  （点击链接或双击物理路径即可查看）
- 页面效果与交互说明：（简要说明 UI 布局、按钮交互体验）

一、用户能做什么
（打开页面后看到什么、能点什么、完成后看到什么）

二、活动规则
（逐条列出规则并标注：已确认 / 默认可推翻 / 待定——依赖存储或登录的项必须标「待定：取决于存储方式」，禁止写成既定事实）

三、对已有数据
（不影响 / 旧数据保留 / 可能影响已有参与记录，请知悉）

四、需要你提供
（名单、图片、文案、截止时间等；没有就写「暂无，先用占位」）

五、待你确认的问题
（不超过 3 个，重点确认 UI 布局与业务决策，不问技术选型）

六、请确认
回复「确认」我继续制作；要改样式或规则直接说即可。
```

## 用词指导（非技术化表达）

确认单中使用自然业务语言，禁止提及技术实现细节：

| 对开发者说 | 不要写 |
|----------|--------|
| 打开页面就能看到候选人列表和票数 | `GET /candidates`、公开读接口 |
| 登录后可以投票 | `POST /vote`、`ensureAuth` |
| 每个用户只能投 1 票 | `unique(puid)`、用户行为表 |
| 投完后按钮变灰，显示已投给谁 | 前端状态管理、API 响应 |
| 不影响其他活动或历史数据 | PostgreSQL、schema |

**整段禁止出现在确认单里：** 表名、字段名、路由路径、文件名、云函数、网关、Bearer token、puid、PostgreSQL、迁移、部署目录、`activity/` 路径、A/B/C/D 分类编号。

## 完整示例

**示例仅演示结构，内容禁止照抄**：示例里的规则（登录、限次等）、文案都是该示例活动的演示内容，不是通用默认；真实确认单的内容只能来自需求单（已确认/默认/待定标注）与决策树。

### 示例 1：新建人气投票（重做类，须确认）

```text
【人气投票】活动方案，请确认

一、用户能做什么
- 打开 H5，看到所有候选人（头像、名字、简介、当前票数）
- 登录后可以投 1 票；投完后按钮变灰，显示「已投给 XXX」
- 列表按票数从高到低排序

二、活动规则
- 每人只能投 1 票，投后不能修改（如需可改票请说明）
- 未登录用户只能浏览，不能投票

三、对已有数据
- 这是全新活动，不影响其他活动或历史数据

四、需要你提供
- 候选人名单（名字、简介、封面图）
- 活动标题/副标题（如有）
- 是否需要活动结束时间？

五、待你确认的问题
1. 投后是否允许改票？（当前方案：不允许）
2. 候选人名单是否已准备好？

六、请确认
回复「确认」我开始制作；要改规则直接说即可。
```

### 示例 2：只改页面（小改类，告知即可）

```text
【人气投票】页面调整，请知悉

一、会改什么
- 候选人卡片样式调整（字号、间距）
- 投票按钮文案改为「为 TA 投票」

二、不会改什么
- 每人 1 票、投后不可改等规则不变
- 已有投票记录不受影响

三、需要你提供
- 无；按现有素材直接改

如有异议请直接说，无异议我按此修改。
```

### 示例 3：改投票规则（改规则类，须确认）

```text
【人气投票】规则调整，请确认

一、拟调整
- 原规则：每人 1 票，投后不可改
- 新规则：每人 1 票，投后 24 小时内可改投 1 次

二、对已有数据
- 已投票用户：改票机会从调整生效时起算
- 历史票数保留，不因改规则清零

三、待你确认的问题
1. 改票窗口是否确认为 24 小时？

四、请确认
回复「确认」后我再改；要调整窗口时长请直接说。
```

## Agent 注意

- **可读不可写：** 第 3 步可内部阅读 database.md、backend.md、frontend.md 推导方案；禁止把读到的表名、路由、目录、部署步骤写入确认单或作为第二个章节发给开发者
- 确认单正文只用上面模板和示例的风格；技术实现仅在第 4 步执行，参考 database.md、backend.md、frontend.md
- **禁止流程预告：** 确认单/提问里不写「我会再单独确认」「不会在…一并问」这类 Agent 内部节奏话术；存储等后续确认在下一步自然发生，确认单只需把依赖它的规则标「待定：取决于存储方式」
- **模板与示例禁止照抄：** 模板括号内是「填什么」的提示、示例正文是演示，都不得原样进入确认单；真实内容只来自需求单与决策树
- 「待确认的问题」只问开发者能拍板的事（次数、时限、能否改票、素材是否就绪），不问技术方案
- 开发者回复「确认」后，Agent 根据确认单中的**业务事实**推导表结构与接口，无需再向开发者复述技术细节
- 若开发者提出新业务要求，回到第 3 步更新确认单，不要边做边改规则
