## 根因

### 1. 主因（结构）：玩家不是「开工一部新作」，而是「插进一部现成档期」

玩家的在研作品 = 世界目录里**已经存在**的作品（`state.career.titleId` 指向 world title），
进度基准是世界的开工月，与玩家何时加入无关：

```js
// h5/js/sim/career.js:3057  sim.careerProjectView()
progress = sim.titleProgress(title, detail, state.year, state.month, config);
phase = sim.careerPhaseAt(progress, config);
// sim.titleProgress 的基准是 sim.titleDevStart(title, detail, config) —— 世界开工月
```

游戏里**没有任何**「玩家入职/接手时才开工」的作（除了池作），所以玩家一接手就继承世界的
进度，「阶段」这个词描述的其实是**这个项目的年龄**，不是「玩家在里面投入了多久」。

### 2. 主因（数据）：发售节奏比开发窗口密，公司里永远有一部做了一半的作

| 指标 | 值 |
|---|---|
| 目录真作原工期 中位 | 20 月（平均 21.3） |
| 经 `cycleMult=1.75` 拉长后工期 中位 | **35 月**（平均 37.4） |
| 同公司相邻两作**发售间隔** 中位 | **13 月**（平均 19.8） |
| 「发售间隔 < 拉长后工期中位」的相邻对 | **744 / 900 = 82.7%** |

82.7% 的相邻两作，后一作的开发窗口**整个包住了前一作的发售**。所以「前作刚发售」这个时点，
本公司必然还有一到多部作在做，而且都做了很久。

`cycleMult=1.75` 是**放大器不是源头**——它把工期中位从 20 拉到 35，让重叠更严重：

| | 平均同时在开发的目录作 | 最高 | 有重叠的月份占比 |
|---|---|---|---|
| `cycleMult=1.75` | 1.82 部 | 17 部 | 47.5% |
| `cycleMult=1.00` | 1.12 部 | 11 部 | 24.6% |

但把 cycleMult 关成 1 做对照（D 段），阶段分布只是略好，主症仍在：

| 落在哪个阶段 | 现状(1.75) | 对照(1.00) |
|---|---|---|
| 中期制作 | 40.9% | 38.3% |
| 内容填充 | 27.1% | 25.5% |
| 打磨 | 17.4% | 12.2% |
| 前期 | 9.8% | 18.9% |

**结论：改 cycleMult 解决不了，数据本身的档期密度才是天花板。**

### 3. 帮凶：派工规则主动挑「最旧」的那部

`sim.pickCareerAssignment`（career.js:1759）从「当月覆盖的所有作」里选一部，
排序是 **prestige 降序 → 发售年早者优先**：

```js
pool = pool.slice().sort(function (a, b) {
  var pd = num(b.prestige, 0) - num(a.prestige, 0);
  if (pd) return pd;
  if (a.releaseYear !== b.releaseYear) return a.releaseYear - b.releaseYear;
  return (a.releaseMonth || 1) - (b.releaseMonth || 1);
});
return pool[0];
```

**排序里完全没有「进度」这一维。**「发售最早」= 「做得最久」= 「进度最深」。所以只要
同月有多部候选，规则一定把玩家塞进最旧的那部。

实测（F 段）：783 个「前作发售次月」的时点里，**39.7% 存在一部进度至少浅 0.20 的替代作**，
平均能提早 0.52 段进度。候选集里明明有活路，规则不走。

### 4. 帮凶：`lateJoin` 只拦「外人入职」，不拦「内部换作」

`lateJoin`（`progressMin: 0.7`）只有两个出口：

- `career-mobility.js:361` — 邀约是否生成（`inviteEligible: false` → 后期作不发邀约）
- `career-mobility.js:181` — 挖人成功率 × `hopHireChanceMul`(0.2)
- `career.js:2760` `addCredit` — 后期加入不署名

而**公司内部**从一部作换到下一部作走的是 `assignCareerProject` → `pickCareerAssignment`，
**完全不受 progressMin 约束**。于是出现一个不对称：外部挖人受「后期不邀请」保护，
内部派工却可以随手指一部 80% 的作给你。

### 5. 帮凶：池作（唯一能「从 0 开始」的通道）是最后一档兜底

`assignCareerProject`（career.js:2834）的顺序是：先 `pickCareerAssignment` 挑目录真作，
**只有挑不到**（`!picked`）才走 `sim.startPoolProject` 开池作（进度 0、从当月开工）。

所以「从零开工一部游戏」这条路，只在**公司当月完全没活**时才被允许。而第 2 条已经证明，
公司里几乎永远有活——于是这条路几乎永远不走。

## 修复方向（按「治本程度」排，尚未拍板）

**A. 给玩家一条「专属新作」通道（治本，改动最大）**
不再要求玩家必须是 world title 的乘客。玩家发售后，在本公司找一部**即将开工**的目录作
（`nextCatalogTitle`，start 在近 N 月内）→ 空窗等待到它的开工月 → 从 0% 开始。
风险：`nextCatalogTitle` 兜底曾踩过坑（见 `bug-career-project-swapped-to-virtual.md`），
必须走「等到开工」而不是「挂上去」，否则会重现「挂在几年后才开工的作上 → 判空窗 → 塞池作」。

**B. 派工规则加入进度维（治标，一行级改动）**
`pickCareerAssignment` 排序里最先看进度：优先 `progress` 最小的候选；
或加硬门槛 `progress ≤ lateJoin.progressMin`（0.7），超了才退回旧排序。
实测预期：前期 9.8% → 29.1%，打磨 17.4% → 3.8%（H 段）。**能明显缓解，不能治本**
（中期制作反而 40.9%→51.6%，因为「最浅的候选」仍常常已经是 30~50%）。

**C. 让「阶段」跟着玩家的接手月走（治观感）**
记 `career.joinProgress`，UI 用 `(now − joinMonth) / (release − joinMonth)` 显示阶段。
玩家会看到「我从前期接手，一路做到发售」。代价：同一部作在界面上有两个进度口径
（世界进度 vs 我的进度），做属性成长/贡献结算时要明确用哪个，别两套打架。

**D. 拉稀档期（治本但动数据）**
让同公司相邻作的发售间隔 ≥ 开发窗口（把某些作的 devStart 单独往后推，而不是统一 ×1.75）。
`cycleMult` 是「一刀切前移开工月」，天然制造重叠；改成**按公司档期自适应**才能从数据层根治。
